# DreamDEX Event Contracts: Architecture & Research Notes

This document summarizes our reverse-engineering and research into the DreamDEX Event Contracts protocol on the Somnia Network. It serves as a reference for hackathon judging and future development.

---

## 1. High-Level Architecture & Mechanics

DreamDEX Event Contracts (Binary Prediction Markets) are fully collateralized, zero-fee prediction markets that operate using three main layers:

1. **Smart Contracts (On-Chain):**
   - `BinaryMarketsModule`: The core trading engine (Orderbook) where `createOrder` transactions are sent.
   - `MarketCreatorAdmin` / Oracle Hub: Contracts responsible for resolving markets and deploying new ones.
   - **ERC-6909 Tokens**: Represent the "Up" (Yes) and "Down" (No) positions.
   - **Mechanics**: 
     - 1 unit of collateral (tUSDC / USDso) mints exactly 1 Up and 1 Down token. 
     - **Zero Fees:** There are no entry, settlement, or winnings fees.
     - **Capped Risk:** The most you can lose is your initial stake. Every winning contract pays out exactly 1 USDso at settlement.

2. **The Indexer (Off-Chain Data):**
   - A centralized GraphQL indexer (powered by Envio/Hasura) tracks every market created on the blockchain.
   - The indexer is the **only** way the frontend knows which `marketId` is currently active.
   - *Testnet Issue:* During our development, the Testnet Indexer (`prd.smk.somnia.host/v1/graphql`) went completely offline, returning 404/ENOTFOUND errors.

3. **The Frontend (Client):**
   - Queries the GraphQL Indexer for the active `marketId`.
   - Connects to WebSockets for live orderbook updates (Bids/Asks).
   - Submits signed transactions to the `BinaryMarketsModule`.

---

## 2. Market Lifecycle (Auto-Rolling)

Event Contracts on DreamDEX are **Automated Series**, not user-created markets.

- **Automated Deployment:** A DreamDEX backend bot continuously creates and "rolls" these markets. For example, every 15 minutes, the bot deploys a new `WBTC:USDso` market.
- **Oracle Resolution:** When the timer expires, the admin bot reads the price feed (e.g., Pyth or a Somnia Oracle) and triggers the settlement function on-chain.
- **Permissioned Creation:** Regular users **cannot** permissionlessly create custom binary markets because assigning a resolution oracle is restricted to whitelisted admins (`MarketCreatorAdmin`).

> **Takeaway:** You cannot dynamically generate your own `marketId` on-chain without admin keys. You must trade against the IDs automatically generated by the protocol.

## 3. The "Synthetic Fallback" Solution

Because the hackathon testnet indexer is unstable, we engineered a **Deterministic Synthetic Fallback** in our `useDreamDexMarkets.js` hook. 

### How it works:
1. **Attempt Indexer Query:** The app tries to fetch the real active markets from the DreamDEX GraphQL API.
2. **Graceful Degradation:** If the fetch fails (timeout or 404), the app calculates exactly what the market *should* be based on the current unix clock (e.g., flooring the time to the nearest 15-minute interval).
3. **Valid `bytes32` Generation:** The smart contract requires a perfectly formatted 32-byte hex string. We intercept the fake synthetic ID and deterministically convert it into a valid 66-character hex string (e.g., `0x4254432d31356d2d313732353434...`) so the `viem` / `wagmi` libraries do not crash.
4. **Transaction Interception:** Because the fake `marketId` would revert on-chain, our UI detects if the market is `isSynthetic`. If true, it bypasses the smart contract entirely, simulates a 1.5-second mining delay, and injects a mock transaction hash into the user's portfolio.

> **Result:** The UI remains 100% functional, beautiful, and interactive for a demo, even when the underlying protocol infrastructure fails. If the indexer comes back online, the app automatically disables the mock interceptor and routes real transactions to the blockchain!

## 5. Helpful References

- **DreamDEX Bot Kit:** Reference implementation for interacting with the SDK programmatically.
- **Smart Contract ABI:** Uses the `BinaryMarketsModule` ABI for all trades (`createOrder`) and claims (`redeem`).
- **Precision:** Prices are calculated as probabilities in 1e6 units (e.g., `0.90 = 900000`). Sizes are formatted based on the collateral token's decimals (6 for USDso/tUSDC).

## 6. The Indexer Problem vs. React Crashes (Post-Mortem)

During development, we encountered a severe issue where the application would present a completely blank "white screen" when interacting with the Trade menu. Initially, this was suspected to be instability with the DreamDEX Testnet Indexer. However, deep code inspection revealed that **network infrastructure issues do not crash modern React applications**. 

The "disappearing" UI was traced back to two localized frontend bugs, while the actual testnet indexer issue simply prevented real transactions from being formed.

### A. The Real Testnet Indexer Issue
- **The Problem:** The DreamDEX testnet GraphQL endpoint (`prd.smk.somnia.host/v1/graphql`) is frequently offline or returning 404s.
- **The Impact:** Without the indexer, the frontend cannot discover the `bytes32 marketId` of the live 15-minute BTC market. 
- **Why this is difficult:** The smart contract `createOrder` function explicitly requires a valid, currently active `marketId`. If you submit an expired ID (like the one we scraped `0x...130ca`) or a fake ID, the smart contract immediately reverts the transaction.
- **Wagmi's Behavior:** When the smart contract reverts during the pre-flight simulation (`eth_estimateGas`), the `wagmi` library silently swallows the error to protect the user from wasting gas, meaning the MetaMask popup never appears. We bypassed this by hardcoding a `gas: 500000n` limit, forcing the transaction to the wallet so we could verify the UI wiring.

### B. The Frontend React Crashes (Resolved)
The white screens were actually caused by:
1. **Rule of Hooks Violation:** We conditionally returned `null` while the fake markets were generating, but placed a `useState` hook *below* that return statement. React enforces that hooks must be called unconditionally in the exact same order every render. Violating this instantly crashed the rendering tree.
2. **Strict Parsing Errors:** The "Size" input was directly tied to an Ethereum `parseUnits(size, 6)` call on every render. If the user cleared the input (creating an empty string `""`) or typed a trailing decimal (`"10."`), `parseUnits` threw a fatal runtime error, crashing the app. This was resolved by wrapping the parser in a graceful `try/catch` block.
